## Agentic Workflow (SF8)

> Two things are documented here: the multi-step decision chain built into the system (with its saved reasoning traces), and how an AI agent (Claude Code) was used to build the project.

### Decision-chain traces (the system's agentic workflow)

`recommend_with_checks` in `src/reliability.py` is a decision-making chain: **sanitize** the input, **rank** every song, **rate confidence**, then either **recommend**, **relax** the profile and re-rank, or refuse with **NO STRONG MATCH**. Each step appends what it saw and decided to a trace. This is deterministic rules, not an LLM planning or calling tools; the optional Claude and embedding parsers sit in front of it as the "interpret" step. `python -m src.main --trace` prints a trace for any run, and the committed file [docs/agent_traces.md](docs/agent_traces.md) holds six real traces generated by `python -m src.traces` (normal, contradictory, relaxed, no-match, rejected input, plain-English request). Three of them:

**A plain-English request** (the interpret step runs first)

```
1. [interpret] read "I'm sad, cheer me up" via keywords -> {'mood': 'happy'}; notes: no ANTHROPIC_API_KEY; used keyword fallback
2. [sanitize] received {'mood': 'happy'} -> kept {'mood': 'happy'}; no repairs needed
3. [rank] mode=balanced, scored 18 songs; top 5: Sunrise City (1.00), Rooftop Lights (1.00), Concrete Verses (0.60) ...
4. [confidence] MEDIUM (best score 1.00; HIGH needs >= 0.85, MEDIUM >= 0.6); reasons: only one preference given; scores are not comparable to richer profiles
5. [decision] RECOMMEND: confidence MEDIUM, present the ranked list
```

**A low-confidence request: the chain relaxes the profile and re-ranks**

```
1. [sanitize] received {'genre': 'metal', 'mood': 'romantic', 'energy': 0.05, 'likes_acoustic': False} -> kept {'genre': 'metal', 'mood': 'romantic', 'energy': 0.05, 'likes_acoustic': False}; no repairs needed
2. [rank] mode=balanced, scored 18 songs; top 5: Velvet Hours (0.48), Iron Tide (0.29), Winter Nocturne (0.26) ...
3. [confidence] LOW (best score 0.48; HIGH needs >= 0.85, MEDIUM >= 0.6); reasons: best match scored only 0.48: no song fits this taste well
4. [relax] tried dropping each preference: without 'genre' best score 0.57, without 'mood' best score 0.41, without 'energy' best score 0.71, without 'likes_acoustic' best score 0.40
5. [decision] RELAX: ignore 'energy'; re-ranked, confidence now MEDIUM (best score 0.71)
```

**An unfixable request: NO STRONG MATCH instead of a ranked list**

```
1. [sanitize] received {'genre': 'metal', 'mood': 'romantic', 'energy': 0.0, 'valence': 0.0, 'acousticness': 1.0} -> kept {'genre': 'metal', 'mood': 'romantic', 'energy': 0.0, 'valence': 0.0, 'acousticness': 1.0}; no repairs needed
2. [rank] mode=balanced, scored 18 songs; top 5: Winter Nocturne (0.43), Hollow Lantern (0.32), Velvet Hours (0.27) ...
3. [confidence] LOW (best score 0.43; HIGH needs >= 0.85, MEDIUM >= 0.6); reasons: best match scored only 0.43: no song fits this taste well
4. [relax] tried dropping each preference: without 'genre' best score 0.49, without 'mood' best score 0.58, without 'energy' best score 0.40, without 'valence' best score 0.41, without 'acousticness' best score 0.33
5. [decision] NO STRONG MATCH: relaxing did not reach MEDIUM, so no ranked list is presented as a pick
```

## Design Pattern (SF10)

> Document how AI helped you choose or implement a design pattern.

**Which design pattern did you use?**

The **Strategy pattern**. Each ranking style ("balanced", "genre-first", "mood-first", "energy-focused") is a small `ScoringMode` object. The scoring code stays the same and takes the mode as an input.

**How did AI help you brainstorm or implement it?**

I asked my AI coding assistant (Claude Code) which optional challenge was worth trying. It recommended Challenge 2, and I chose to go ahead with it. The assistant then brainstormed the design and wrote the code, and the result was tested and compared against the earlier output.

**Design reasoning:**

All the scoring weights already lived in one `POINTS` dictionary, and the four modes differ only in how many points each feature is worth. Three designs were possible:

1. **Copy `score_song` once per mode.** This repeats the same logic, so any later fix would have to be made four times.
2. **One class per mode, each with its own scoring method.** This is too much code, because the modes do not score differently. They only weight things differently.
3. **A mode is data: a name plus the weights it changes.** This is a lightweight Strategy pattern. Adding a mode means adding one entry to `MODES`, and the scoring code stays the same.

Option 3 was built. Two details came with it:

- A mode lists only the weights it changes. The rest come from the base `POINTS`. The weights are looked up when a song is scored, so the earlier scratch experiments that patch `POINTS` still work.
- Unknown modes fail with a clear error, and the command line only accepts valid names.

The work was done on a separate branch (`experiment/scoring-modes`), following the challenge's advice, so the working version on main stays safe.

**How does the pattern appear in your final code?**

- `ScoringMode` (a frozen dataclass), `MODES` and `get_mode()` in [src/recommender.py](src/recommender.py).
- `score_song(..., mode="balanced")` and `recommend_songs(..., mode="balanced")` take the mode. `Recommender(songs, mode=...)` stores it.
- [src/main.py](src/main.py) has `--mode NAME` to run one mode and `--compare` to show the top 3 of every mode side by side.
- Tests are at the end of [tests/test_recommender.py](tests/test_recommender.py).

**What I verified or fixed manually:**

- The default run (`balanced`) is byte-for-byte identical to the run before the change.
- Perfect matches score 1.0 and worst matches score 0.0 in every mode, so scores stay between 0 and 1 whatever the weights add up to.
- I checked that the modes really differ: for the same profile, `genre-first` and `mood-first` pick different top songs. Before, I had guessed that weight changes would barely matter. That was only partly right.
- The assistant made a mistake while editing `main.py`. Some `\n` escapes in the code it wrote were broken, which caused a syntax error. I caught it when the program failed to start. The assistant then rewrote the block, and I re-ran the program, the comparison and all 18 tests.
